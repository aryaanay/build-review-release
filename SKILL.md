# Build, review, and release

1. Inspect the current project, the target platform, and the evidence behind the brief. Identify the intended audience, deliverable, constraints, and acceptance checks. For substantial builds, share the plan and the highest-impact tradeoffs before implementation.
2. Route the work through the available skills. Use the engineering guidance for code. For original visual work, consider Hallmark and Apple design, respect the project's existing design system, and review real references. Read [the tool guide](references/tools.md) when choosing between overlapping resources.
3. Implement the smallest complete workflow. Keep dependencies pinned where the project supports it and review new permissions, dependencies, and costs before enabling them.
4. Exercise the main user flow and a relevant failure case. For visual work, inspect rendered desktop and mobile states and test keyboard access and reduced motion where applicable. Run appropriate checks for security, accessibility, and user-facing copy. Record the checks run and results actually observed.
5. Publish original work only within the user's authorized scope. Confirm repository ownership, visibility, branch, attribution, and license. Inspect the release diff for secrets and private data, and verify any recurring workflow will stay within the user's spending limit. Verify the GitHub URL, commit or pull request, and available checks after publication.
